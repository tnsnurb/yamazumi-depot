# Архитектура проекта (Yamazumi Depot)

Этот документ описывает основные архитектурные решения и правила разработки проекта.

## Структура сервера

Для поддержания чистоты кода и масштабируемости используется многоуровневая структура:

* `server.js`: Основной входной файл. Теперь это минималистичный "загрузчик", который настраивает сервер и подключает маршруты.
* `src/routes/`: Определение API-эндпоинтов. Использует цепочки middleware для авторизации.
* `src/controllers/`: Слой контроллеров. Содержит всю бизнес-логику.
  * `locomotiveController.js`: Управление парком и тех. данными.
  * `remarkController.js`: Жизненный цикл замечаний (добавление, фото, статусы).
  * `movementController.js`: Логика перемещений и безопасный экспорт.
  * `dictionaryController.js`: Управление всеми справочниками системы.
  * `profileController.js`: Личные данные и безопасность пользователя.
  * `adminController.js`: Системные логи и аудит.
* `src/services/`: Слой сервисов. Содержит сложные расчеты и хелперы (например, `locomotiveService.js`).
* `src/config/`: Настройки Express, сессий и безопасности (Helmet, CORS).

## Структура фронтенда

Для поддержания типизации и чистоты UI используется сервисный подход:

* `frontend/src/api/apiClient.ts`: Базовый клиент-обертка над `fetch`. Обрабатывает JSON, заголовки и преобразует сетевые ошибки в читаемые `ApiError`.
* `frontend/src/api/locomotiveService.ts`: Слой сервисов, предоставляющий строго типизированные Async-методы для UI компонентов.
* `frontend/src/types/`: Общие TypeScript интерфейсы (например, `Locomotive`, `LocoStatus`), гарантирующие соответствие данных между API и компонентами.

## Безопасность и Авторизация

### Middleware (Плоская структура)

Для авторизации используется цепочечный подход (Flat Middleware):

* `requireAuth`: Проверяет JWT или сессию.
* `requireAdmin`: Проверяет наличие прав администратора.
* `requirePermission('key')`: Проверяет конкретное разрешение.

**Важно:** Каждая проверка требует наличия `requireAuth` перед собой в цепочке роута: `[requireAuth, requireAdmin]`.

### Безопасность данных

1. **CSV Injection**: Экспорт данных (например, перемещений) выполняется через библиотеку `exceljs`, которая автоматически экранирует опасные символы.
2. **Атомарность**: Все критические изменения (смена статуса + начисление баллов + логирование) выполняются через **Supabase RPC** функции. Это гарантирует, что база данных никогда не останется в промежуточном (битом) состоянии.

## Правила разработки

1. **DRY (Don't Repeat Yourself)**: Если логика используется более чем в одном месте, она ДОЛЖНА быть вынесена в `src/services/` (бэкенд) или `src/api/` (фронтенд).
2. **Explicit Auth**: Всегда явно указывайте цепочку middleware в серверных роутах.
3. **Frontend API Pattern**: Запрещено использовать прямой `fetch` или `axios` внутри React-компонентов. Все запросы должны идти через методы `locomotiveApi` или аналогичных сервисов. Это гарантирует типизацию и централизованную обработку ошибок.
4. **Разделение ответственности**: Route -> Controller -> Service. SQL-код должен быть минимален в контроллерах и сосредоточен в сервисах или RPC (Postgres функций).
5. **Атомарность**: Для критических действий, затрагивающих несколько таблиц (например, перемещение локомотива), используются **Supabase RPC** функции.
6. **Единый источник истины**: Функция `resolveLocoId` из `locomotiveService.js` — единственный способ идентификации локомотива по вводу пользователя.

## База данных

Проект использует **Supabase**. Основная логика безопасности (RLS) и некоторые бизнес-процессы (атомарные функции) реализованы на стороне БД для максимальной надежности.

## Новые системы и модули

### 📊 Система Метрологии и Контроля (Gauges)

* **Слой данных**: Используется таблица `gauges`, связанная с `locomotives`. Статусы приборов («На складе», «На локомотиве», «На поверке», «Списан») строго синхронизированы с бизнес-логикой перемещений.
* **Мобильный Терминал**: Изолированная страница `/gauges/terminal`, оптимизированная под работу «в полях». Поддерживает как потоковое QR-сканирование (`html5-qrcode`), так и ручной ввод серийных номеров.
* **Интеграция QR**: Для управления используется префикс `gauge:`, что исключает ложные срабатывания при сканировании других типов меток.

### 🔄 Управление Циклами Ремонта (Service Sessions)

* **Контейнер данных**: Все активности (замечания, чеклисты, замеры) группируются внутри «Ремонтной сессии» (`repair_sessions`).
* **Сквозная идентификация (Work Order)**: Внедрена система генерации номеров заказов в формате `WO-[Локо]-[ID]`. Это обеспечивает связь цифровой записи с физическим архивом документов.

## Стандарты Дизайна и UI

Для поддержания профессионального и «премиального» вида приложения следуйте этим правилам:

1. **Типографика**: Основной шрифт — **Inter**. Максимальный вес для заголовков — `SemiBold 600`. Избегайте использования `Bold 700` или `Black 900`, чтобы интерфейс оставался легким.
2. **Регистр текста**: Все заголовки страниц и элементов пишутся в **Предложенном регистре** (Sentence case). Использование `CAPS` (заглавных букв) запрещено, кроме аббревиатур.
3. **Цветовая палитра**:
   - **Primary**: Синий `blue-600` (`#2563eb`) — единый цвет для всех разделов (Карта, Ремзона, Метрология).
   - **Success**: Изумрудный `emerald-600` — для статуса «Исправен» или завершенных действий.
   - **Critical**: Розовый `rose-600` — для дефектов и просроченных поверок.
4. **Минимализм**:
   - Убраны все декоративные вертикальные линии (`border-l-4`) перед заголовками.
   - Запрещено использовать крупные декоративные иконки в цветных блоках рядом с заголовками страниц. Заголовок должен быть чистым и текстовым.

## Инфраструктура и Деплой

* **Reverse Proxy**: Nginx настроен как прокси для Node.js бэкенда.
* **Безопасность (SSL)**: Автоматическое управление сертификатами через Certbot (Let's Encrypt). Для работы камер в Терминале наличие HTTPS является обязательным требованием браузера.
* **Менеджер процессов**: Использование PM2 гарантирует автоматический перезапуск сервера при сбоях и после обновления кода.
